# «Проявитель» — AI-сервис платформы «Пульс»

Интеграция с «Пульсом» отложена до готовности его backend. Автономный стенд сохраняет
синтетические данные и задачи. Для команды подготовлены:
[требования к backend](docs/backend-handoff.md), [JavaScript-клиент](clients/javascript/README.md),
[эксплуатация и восстановление](docs/operations.md), `deploy/nginx-assistant.conf`.
Общие квоты сервиса: 60 запусков/минуту, 1000/24ч, 8 параллельно (миграция `0008`).
Настройки `AI_GLOBAL_GENERATION_REQUESTS_PER_MINUTE`, `AI_GLOBAL_GENERATION_REQUESTS_PER_DAY`,
`AI_GLOBAL_MAX_CONCURRENT_GENERATIONS` действуют во всех процессах через БД.

Добавлены ограничения новых ответов на пользователя: 20/минуту, 200 за скользящие
24 часа, две одновременные генерации. Настройки — `AI_GENERATION_REQUESTS_PER_MINUTE`,
`AI_GENERATION_REQUESTS_PER_DAY`, `AI_MAX_CONCURRENT_GENERATIONS_PER_USER`.
Миграция `0007` добавляет синхронизацию через БД для нескольких процессов. При
превышении API возвращает 429 с `Retry-After`; тестовый чат показывает время ожидания.
Replay не расходует квоту. Это ограничение запусков, не денежный лимит провайдера.

План дальнейшей реализации, независимый от временного тестового интерфейса:
[docs/implementation-plan.md](docs/implementation-plan.md).

Тестовый директор может попросить ассистента предложить задачу по станку.
Инструмент `propose_task` сохраняет только предложение, затем пользователь нажимает
«Подтвердить создание» или «Отклонить». В demo подтверждение создаёт синтетическую
задачу в БД AI-сервиса; основной backend не изменяется. Повтор подтверждения возвращает
тот же результат. Предложение действует час, его payload неизменяем; права проверяются
повторно. Для остальных тестовых ролей право `tasks:create` не выдано.
Реальный POST /tasks остаётся закрыт до согласования контракта и идемпотентности.

Локальный Python стенда хранится в `.runtime/python` внутри проекта; `.runtime/`
исключена из Git. Временные папки ОС больше не являются зависимостью запуска.

Инструменты чтения: `get_stations`, `get_defect_summary`, `search_knowledge`
и `read_knowledge_article`.
Локальная проверка без API-ключа и LLM: `ai-service/.venv/bin/python scripts/check_tools.py`.
Модель уже может автоматически вызывать эти инструменты: SSE сообщает `tool_start`
и `tool_end`, а результат возвращается модели для итогового ответа. Вызовы и источники
сохраняются в БД (миграция `0003`). Отдельно доступно предложение тестовой задачи
с обязательным подтверждением пользователя.

Для проверки знаний напишите в новом чате: «Найди инструкцию по проверке качества
термопереплёта st-03 и укажи источник». Локальный адаптер возвращает синтетическую
инструкцию с версией и датой; сотрудник производства не видит документ закрытого
участка. Реальный поиск использует `/kb/search` с JWT пользователя. Чтение полных
статей на реальном backend пока не включено: в исходном контракте нет схемы их тела.
При чтении истории доступ к использованным документам проверяется заново;
отзыв доступа блокирует историю и продолжение этого диалога.

Первый backend-этап: собственные диалоги, история, контекст модулей и потоковые ответы.
Frontend подключается к API на порту **8081**. Основной API платформы остаётся на **8080**.

Context Manager сохраняет модуль, станок и период за пределами текстового окна модели.
Для уточняющих вопросов можно не передавать `context` повторно. Новый `context` заменяет
предыдущий целиком. `reset_context: true` начинает новую тему: прежняя история остаётся
в БД, но не передаётся модели. В тестовом чате это пункт «Очистить контекст диалога»
в списке модулей. Снимок контекста ответа доступен в SSE `context` и истории;
изменение требует миграции `0005`.

Для новых ответов ведётся журнал запусков (`analysis_runs`, миграция `0006`).
В тестовом чате под ответом видны время до первого текста и общая длительность;
раскройте строку для подготовки контекста, обращений к модели, повторов, инструментов
и traceId. После обновления страницы данные сохраняются. API журнала:
`GET /assistant/conversations/{id}/runs?limit=20&offset=0`; та же диагностика
возвращается в `messages[].diagnostics` и SSE `diagnostics` перед `done`.
Повтор с прежним Idempotency-Key возвращает исходные замеры без нового запуска.
Расход токенов учитывается только по полученному `usage`; неизвестные значения
остаются `null`, частичный учёт явно отмечается. Старые ответы не пересчитываются.
Содержимое сообщений и ключи в отдельный журнал диагностики не копируются.

`GET /assistant/capabilities` с JWT возвращает возможности текущего пользователя:
режимы ответа, допустимые модули/сущности контекста, инструменты, подтверждаемые
действия и действующие лимиты. Секреты не возвращаются, модель не вызывается.
Ответ описывает настроенные интеграции, а не доступность внешней сети. Отдельно
отмечены синтетические данные и незавершённые контракты основного backend.
Тестовый чат получает отсюда доступные режимы и фильтрует свои пункты модулей;
его временный набор экранов не ограничивает контракт будущего frontend.

## Подключение AIAI.BY

Быстрый режим DeepSeek: `AI_LLM_THINKING=disabled`, `AI_LLM_MAX_TOKENS=1024`.
Проверка модели кэшируется на час и запускается в фоне при старте; HTTP-соединения
сохраняются до 120 секунд. Ответы по умолчанию краткие, подробности — по запросу.
Настройка thinking описана в [официальной документации DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode/).
Временные ошибки сети и HTTP 408/429/5xx повторяются до двух раз **только до первого текста**.
Уже начатый ответ не генерируется повторно автоматически. При обрыве сохраняется
частичный текст и показывается конкретная причина с traceId; секреты в лог не попадают.
Пустые delta и подтверждённый finish_reason обрабатываются корректно; незавершённый
поток без маркера завершения остаётся ошибкой. Задержка самого провайдера не гарантируется.

Для локального тестового чата с настоящей моделью можно явно задать
`AI_MODE=llm` и `AI_ALLOW_DEMO_LLM=true` в `ai-service/.env`.
Это исключение для локального стенда с demo-пользователями: сообщения и история
уйдут провайдеру, поэтому вводите только тестовые данные. Синтетический сценарий
производства остаётся помеченным как demo. Для рабочего развёртывания используйте JWT платформы.

Настройки провайдера — в `ai-service/.env.example`; локальные значения — в
`ai-service/.env` (игнорируется Git). Из корня проекта:

```bash
cp -n ai-service/.env.example ai-service/.env
# Откройте ai-service/.env в редакторе и вставьте ключ в AIAI_API_KEY.
ai-service/.venv/bin/python scripts/check_llm.py --list
# Укажите AI_MODEL точно как в полученном списке.
ai-service/.venv/bin/python scripts/check_llm.py
```

`--list` запрашивает каталог; команда без флага отправляет короткий платный
тестовый запрос и печатает ответ потоком. Ключи, заголовки и тела ошибок не печатаются.
Перед генерацией ID модели обязательно проверяется по `/models` выбранного endpoint.
Автоматической подмены модели нет.

Переменные: `AI_PROVIDER=aiai`, `AI_BASE_URL`, `AI_MODEL`, `AIAI_API_KEY`.
Старые `AI_LLM_BASE_URL`, `AI_LLM_MODEL`, `AI_LLM_API_KEY` остаются совместимыми.
Публичная [документация провайдера](https://aiai.by/docs) указывает
`https://api.aiai.by/v1`. Переданный в задании `https://vedai.by/api/v1`
публичной документацией не подтверждён: используйте его только после сверки с кабинетом.
Запрошенный `deepseek-v4-flash` оставлен неподтверждённым кандидатом, не выбран по умолчанию.
Страница [DeepSeek V4.1 Flash](https://aiai.by/models/deepseek-v4-1-flash)
публикует другой ID — `deepseek-v4.1-flash`; он также не подставляется автоматически.

CLI-проверка провайдера не требует JWT платформы. Для включения настоящей модели
в API задайте `AI_MODE=llm` и настройте `AI_AUTH_MODE=jwt` по разделу ниже.
Действующий demo-чат остаётся в demo-режиме, пока интеграция не настроена;
локальные demo-пользователи отправляют историю внешней модели только при явном AI_ALLOW_DEMO_LLM=true.
При Docker-запуске перенесите настройки провайдера в корневой `.env`,
который передаётся контейнеру через Compose. Файлы с ключами в образ не копируются.

## Простой тестовый интерфейс

Над полем ввода выбирается **Обычный чат** или **Подробный разбор** для следующего
сообщения. Обычный режим — без thinking; подробный — thinking с high effort,
лимитом 8192 токена и ожиданием до 300 секунд. Выбор сохраняется с сообщением
и не влияет на другие запросы. Внутренние черновые рассуждения не показываются:
сначала статус «Подробно разбираю вопрос…», затем итоговый ответ.

Текст выводится по мере получения SSE. Большие полученные фрагменты плавно
дорисовываются в браузере; после конца потока очередь догоняет текст за ≤250 мс.
Паузы самого провайдера скрыть невозможно. При reduced motion и replay анимации нет.

После запуска откройте **<http://127.0.0.1:8081/>**. Отдельный frontend-процесс не нужен.

- Нажмите «Почему вырос процент брака?» или напишите свой вопрос.
- Контекст производства и станка №3 уже заполнен. Его можно менять над чатом.
- Слева доступны сохранённые диалоги и выбор demo-пользователя.
- «Проверить изоляцию пользователей» проверяет отказ в чтении текущего диалога другим пользователем.
- «Остановить» прерывает ответ; «Восстановить ответ» возвращает результат после потери соединения.
- Токены выдаются автоматически для трёх фиксированных demo-пользователей и хранятся только в памяти страницы.

Страница и локальный `POST /demo/session` включены только при `AI_AUTH_MODE=demo`
и `AI_DEMO_UI_ENABLED=true` (по умолчанию). Demo-вход требует того же Origin и
имени хоста `127.0.0.1`, `localhost` или `::1`. Порт сервиса оставляйте привязанным
к loopback, как в Compose: эта страница предназначена для локального тестирования.
В demo между фрагментами ответа есть небольшая пауза, чтобы было удобно проверить
поток и остановку. Настройка: `AI_DEMO_CHUNK_DELAY_SECONDS` (по умолчанию 0.06).
При `AI_AUTH_MODE=jwt` страница и demo-вход отсутствуют. Можно отдельно отключить
тестовый интерфейс через `AI_DEMO_UI_ENABLED=false`, сохранив demo API и CLI-токены.

## Запуск с PostgreSQL

Нужны Docker с Compose и Python 3 для генерации локальной конфигурации.
Из корня проекта:

```bash
python3 scripts/init_demo.py
docker compose up --build -d
```

Compose запускает PostgreSQL 16, применяет Alembic-миграции отдельным процессом
и только затем запускает AI-сервис. Диалоги сохраняются в томе `assistant-data`.
`docker compose restart ai-service` сохраняет историю.

- Swagger: <http://localhost:8081/docs>
- Проверка БД и миграций: <http://localhost:8081/health/ready>
- Остановка: `docker compose down` (том сохраняется).

Для демонстрации не нужны внешний LLM, ключ модели или основной backend.
`init_demo.py` создаёт `.env` с уникальными случайными секретами; повторный запуск его не меняет.

## Локальный запуск без Docker

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/getting-started/installation/).
Для удобства этот вариант использует SQLite-файл; основной вариант хранения — PostgreSQL.

```bash
python3 scripts/init_demo.py
uv sync --project ai-service --python 3.12 --extra dev --frozen
uv run --project ai-service alembic -c ai-service/alembic.ini upgrade head
uv run --project ai-service uvicorn app.main:create_app --factory --port 8081 --no-access-log
```

Если зависимости уже установлены, можно без uv:

```bash
ai-service/.venv/bin/alembic -c ai-service/alembic.ini upgrade head
ai-service/.venv/bin/uvicorn app.main:create_app --factory --port 8081 --no-access-log
```

Для внешнего PostgreSQL замените `AI_DATABASE_URL` на
`postgresql+asyncpg://USER:PASSWORD@HOST:5432/DATABASE` и примените миграции.
Миграции выполняются отдельно от web-процессов. Таблицы автоматически при запуске API не создаются.

## Проверка демо

При локально установленных зависимостях:

```bash
ai-service/.venv/bin/python scripts/smoke_demo.py
```

Или через контейнер, без установки Python-зависимостей на хост:

```bash
docker compose exec -T ai-service .venv/bin/python - < scripts/smoke_demo.py
```

Скрипт создаёт диалог, выводит SSE-ответ, проверяет сохранение и запрет доступа другому пользователю.
В контейнере он использует переменные окружения Compose; в локальном запуске читает `.env`.

Для ручного подключения frontend выдайте demo-токен (действует час):

```bash
ai-service/.venv/bin/python scripts/demo_token.py director
```

В контейнере:

```bash
docker compose exec -T ai-service .venv/bin/python - director < scripts/demo_token.py
```

Варианты: `director` — все demo-модули и подразделения; `worker` и `other` — только производство.
У `other` отдельный `sub`, поэтому диалоги первого пользователя ему недоступны.
В Swagger нажмите **Authorize** и вставьте JWT. Основной API не выдаёт токены;
локальный тестовый интерфейс использует отдельный ограниченный `/demo/session`.

## Что реализовано

| Маршрут | Результат |
| --- | --- |
| `POST /assistant/conversations` | Диалог текущего пользователя, `201` |
| `GET /assistant/conversations` | Список с `limit` и `offset` |
| `GET /assistant/conversations/{conversation_id}` | Диалог и страница сообщений |
| `POST /assistant/conversations/{conversation_id}/messages` | Сохранение запроса и SSE-ответ |

Даты — UTC. Идентификаторы диалогов и сообщений — UUID. Другой пользователь получает `404`.
Доступ к сохранённому контексту проверяется заново и при чтении истории, и перед продолжением разговора.
POST поддерживает необязательный `Idempotency-Key`: 8–128 букв, цифр, `_` или `-`.
Повтор того же ключа возвращает сохранённый результат. Изменённый запрос с тем же ключом — `409`.
Одновременно в диалоге формируется только один ответ, блокировка хранится в БД и работает между процессами.

Параметры истории: `message_limit=100` (до 500) и `message_offset=0`.
Нулевой offset возвращает последние сообщения, в хронологическом порядке; offset считается с конца.
Порядковые номера `sequence` позволяют сопоставить страницы.

Подробный контракт SSE и пример frontend: [docs/integration.md](docs/integration.md).

## Режимы модели и доступа

`AI_MODE=demo`: детерминированный русскоязычный сценарий со станком `st-03`,
за 1–11 ноября 2026 года. Данные синтетические: брак 6% против 2% в предыдущем периоде.
Для других станков и периодов цифры не подставляются. В ответе и событии `sources`
демо-источник явно обозначен. Последующие вопросы используют сохранённый контекст.
Это сценарий для проверки интеграции, свободный анализ любых вопросов требует LLM.

`AI_MODE=llm`: потоковые ответы совместимого `/chat/completions` API.
Нужны `AI_LLM_BASE_URL`, `AI_LLM_MODEL`, `AI_LLM_API_KEY` и `AI_AUTH_MODE=jwt`.
Имена моделей не зашиты в код. История ограничена последними 40 сообщениями и 80 000 символами;
частичные ответы модели не отправляются обратно как достоверная история.
Реальные бизнес-данные и действия пока не подключены, и это явно отражается в системном контексте.
Адаптер использует [документированный SSE-протокол Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).

`AI_AUTH_MODE=demo`: HS256 с локальным случайным секретом и серверной demo-ACL.
С внешним LLM этот режим требует явного AI_ALLOW_DEMO_LLM=true и включённого локального тестового интерфейса.

`AI_AUTH_MODE=jwt`: только RS256, явно заданные issuer/audience, проверка `exp`, `iat`, `sub`;
нужен ровно один источник ключей — `AI_JWT_PUBLIC_KEY` либо `AI_JWT_JWKS_URL`.
URL JWKS задаётся оператором, адреса из JWT-заголовков не используются.
`AI_PLATFORM_BASE_URL` обязателен: сервис запрашивает `/me` с пользовательским JWT,
сверяет `id` с `sub` и берёт актуальные `permissions` и `departmentScope`.
Для доступа нужны `assistant:use` и `<module>:read`.
Это соглашение интеграции: исходный OpenAPI не задаёт названия permissions и параметры JWT.

Станки проверяются по `/equipment/stations`, который основной backend обязан фильтровать
по пользовательским правам. Произвольные сущности не допускаются: для них нужен новый серверный адаптер.
Совмещение station и department в production-режиме отклоняется: в исходной схеме Station
нет departmentId, и сервер не может подтвердить эту связь.
При недоступности проверки прав доступ закрывается. Отказы записываются в таблицу `assistant_audit`.

## Ошибки и восстановление

До начала потока: RFC 7807 `application/problem+json`, поля `title/status/detail/traceId`.
После HTTP 200 ошибки приходят событиями `error` и `done` со статусом `failed`.
После `done` ответ уже сохранён. Обрыв клиента сохраняет частичный текст со статусом `cancelled`.
При аварии процесса блокировка истекает через `AI_STREAM_TIMEOUT_SECONDS + 30` секунд;
следующее чтение/сообщение отмечает старый ответ `interrupted` и освобождает диалог.
Во время генерации частичный текст сохраняется примерно раз в секунду.
SSE не поддерживает возобновление по `Last-Event-ID`; используйте историю или повтор с тем же Idempotency-Key.
Не переподключайте POST автоматически с новым ключом.

Таймаут генерации по умолчанию — 120 секунд, heartbeat — 10 секунд,
предел ответа — 40 000 символов. CORS задаётся JSON-массивом `AI_CORS_ORIGINS`.
Прокси должен пропускать SSE без буферизации и иметь таймаут больше времени генерации.
Логи приложения содержат только код ошибки и traceId; содержимое запросов, JWT и ошибки провайдера не логируются.
