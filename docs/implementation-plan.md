# План реализации AI-сервиса «Проявитель»

Состояние проекта: 12 ноября 2026 года. Это план дальнейшего развития существующего
сервиса, а не задание на его повторное создание.

## 1. Цель и границы

«Проявитель» — самостоятельный backend платформы «Пульс». Он получает вопрос и
контекст, проверяет полномочия, извлекает доступные данные, выполняет проверяемые
расчёты и возвращает ответ с источниками. Действия в платформе выполняются после
подтверждения пользователя.

Основной сценарий первого законченного MVP:

> Пользователь спрашивает о росте брака → ассистент проверяет показатели и станки →
> объясняет изменения и ограничения → находит подходящую инструкцию → предлагает
> задачу → после подтверждения создаёт её в «Пульсе» и показывает результат.

### Интерфейс разрабатывается отдельно

- Текущая страница чата — временный тестовый стенд. Её внешний вид, компоненты и
  расположение кнопок не являются требованиями к будущей платформе.
- Будущий интерфейс сможет вызывать сервис из общей страницы ассистента, боковой
  панели или любого бизнес-модуля через одинаковый HTTP/SSE-контракт.
- Backend не зависит от DOM, frontend-фреймворка и текущих названий элементов экрана.
  `screen` — необязательная информационная метка; права из неё не выводятся.
- История, выбранный режим, источники, статусы и предложения действий хранятся на
  сервере. Их можно восстановить после закрытия любого клиента.
- Плавное визуальное появление текста — ответственность клиента. Backend передаёт
  поступившие фрагменты сразу. События должны быть пригодны и для клиента без анимации.
- Demo-пользователи и локальная выдача токенов не используются для авторизации
  будущего рабочего интерфейса.

### Разделение ответственности

| Участник | Отвечает за |
| --- | --- |
| AI-сервис | Диалоги, работа с LLM, инструменты, контекст, источники, предложения действий, собственный аудит |
| Основной backend «Пульса» | Бизнес-данные и операции, профиль пользователя, права на сущности, фильтрация данных по доступу |
| Frontend платформы | Внешний вид, открытие ассистента, передача контекста и JWT, отображение событий и подтверждений |
| AIAI.BY | Выполнение запросов к модели; задержки и доступность провайдера учитываются отдельно от нашего сервиса |

Шесть блоков архитектуры реализуются модулями одного AI-приложения. Отдельными
компонентами развёртывания остаются AI-сервис, его PostgreSQL и основной backend.

## 2. Что уже реализовано

Актуальное ограничение от 12 ноября 2026: интеграцию с «Пульсом» не выполнять до
готовности backend другого разработчика. Рабочие JWT/данные/запись реальных задач
и совместная приёмка отложены. Автономные части продолжают работать с синтетическим
адаптером; требования для согласования вынесены в `docs/backend-handoff.md`.

| Блок | Текущее состояние | Что осталось |
| --- | --- | --- |
| LLM Orchestrator | AIAI.BY, поток ответов, standard/deep, цикл инструментов, проверяемые результаты, диагностика задержек и попыток | Бюджеты расхода и расширение сценариев |
| Context Manager | Отдельный слой: модуль, сущность, фильтры, наследование вне текстового окна, явный сброс, снимок контекста ответа, ограничения истории | Правила остальных сущностей и адаптеров |
| Tool Executor | Реестр, схемы/права, станки, агрегат брака, поиск/чтение знаний; журнал и длительность вызовов, синтетический адаптер | Остальные бизнес-инструменты и реальные агрегаты |
| Conversation Store | История, режимы, источники, вызовы инструментов, запуски с временами/ошибками, идемпотентность и восстановление | Retention и эксплуатация на рабочем PostgreSQL |
| RAG / Knowledge | Поиск с JWT и метаданными, синтетические статьи, повторная проверка ACL в истории | Схема реальных статей и проверка с основным backend |
| Policy & Audit | JWT, изоляция, ACL контекста/знаний, аудит, предложения синтетических задач с подтверждением | Реальные действия, ограничения частоты/расходов и полный эксплуатационный аудит |

В репозитории есть подготовка PostgreSQL/Docker и миграции; текущий локальный стенд
использует SQLite. Основного backend «Пульса» здесь нет: есть его исходный OpenAPI.
Проверки JWT и интеграционные адаптеры ещё нужно проверить с настоящим backend платформы.

## 3. Этап 0 — согласовать контракт интеграции

**Результат:** frontend и основной backend могут разрабатываться параллельно с AI-сервисом.

Сохранить существующие маршруты:

- `POST /assistant/conversations`
- `GET /assistant/conversations`
- `GET /assistant/conversations/{id}`
- `POST /assistant/conversations/{id}/messages`

Зафиксировать в OpenAPI:

- `text`, необязательный `context`, режим `reasoning_mode: standard | deep`;
- принадлежность диалогов пользователю и правила JWT;
- пагинацию, UTC, Idempotency-Key, ошибки RFC 7807;
- SSE-события `meta`, `status`, `sources`, `delta`, `error`, `done`;
- сохранение результата до `done`, отмену, восстановление и поведение при повторе запроса;
- форматы ссылок на источники и ссылок на сущности платформы.

Согласовать с основным backend:

1. Адрес API, issuer/audience JWT, источник ключей и точную структуру `/me`.
2. Названия permissions. Используемые сейчас `assistant:use` и `<module>:read` —
   соглашение нашего сервиса; исходная спецификация не задаёт полный справочник прав.
3. Какие списки гарантированно фильтруются по текущему пользователю.
4. Связь станка с подразделением: в исходной схеме Station отсутствует departmentId.
5. Недостающие схемы ответов, прежде всего GET `/production/defects`,
   `/finance/unit-economics` и содержимое статьи базы знаний.
6. Откуда берутся число всех заказов, число бракованных заказов и сравнимый прошлый
   период. Одного списка дефектов недостаточно для вычисления процента брака.
7. Единицы, часовой пояс периодов, гранулярность, правила подсчёта и время обновления.

Реализован `GET /assistant/capabilities`: доступные режимы, модули и типы контекста,
инструменты, подтверждаемые действия и лимиты для текущего пользователя. Настроенные
интеграции отделены от незавершённых контрактов; права модуля не выдаются за наличие
бизнес-данных. Ответ не кэшируется между пользователями, не вызывает LLM и не содержит
секретов. Список режимов использует ту же функцию, что и проверка сообщения.
Тестовый чат получает capabilities при входе/смене пользователя/обновлении и скрывает
недоступные режимы и пункты модулей. Новый frontend использует весь контракт независимо
от временного тестового интерфейса. Проверены роли директора/сотрудника в браузере,
изменение профиля JWT и отсутствие LLM-вызовов при получении возможностей. Если
capabilities не удалось загрузить, тестовый frontend не использует прежний список прав.

**Готово, когда:** участники имеют один контракт с примерами успешного ответа,
отказа в доступе, частичного сбоя и отмены. Неопределённые ответы основного API
описаны или явно выделены как зависимости дальнейшей интеграции.

## 4. Этап 1 — клиент «Пульса», контекст и инструменты чтения

Начато: добавлены `app/pulse.py` (типизированный PulseClient и синтетический адаптер)
и `app/tools.py` (реестр, JSON Schema, проверка прав и исполнитель). Первые функции:
`get_stations` и `get_defect_summary`. Доступна локальная проверка
`ai-service/.venv/bin/python scripts/check_tools.py` без LLM и внешней сети.
Executor регистрируется в состоянии приложения. Подключён первый цикл вызовов
моделью, журнал инструментов и SSE-события их выполнения; подробности — в этапе 2.
Реальный список станков поддержан по существующему контракту; реальная агрегированная
сводка брака требует согласования схемы и намеренно возвращает unavailable.

**Результат:** сервис получает показатели через адаптеры вместо встроенных в prompt чисел.

Добавить `PulseClient` для обращения к основному API с пользовательской авторизацией.
Реальные HTTP-ответы преобразуются в собственные типизированные DTO AI-сервиса.

Первый набор инструментов:

| Инструмент | Маршрут «Пульса» | Назначение |
| --- | --- | --- |
| `get_pulse_metrics` | `/metrics/pulse` | KPI, план/факт, сигналы |
| `get_defect_breakdown` | `/production/defects` | Разбивка брака за доступный период |
| `get_stations` | `/equipment/stations` | Состояние доступных станков |
| `get_unit_economics` | `/finance/unit-economics` | Финансовые последствия при наличии права на финансы |

Для каждого инструмента определить схему аргументов и результата, требуемые права,
таймаут, допустимые фильтры, предел объёма ответа и сведения об источнике.
Модель выбирает только зарегистрированные функции; произвольные URL и SQL не исполняются.
Недоступные инструменты не передаются модели, но сервер всё равно проверяет каждый вызов.

Вынесен `app/context_manager.py`: проверки доступа, наследование структурированного
контекста по всему диалогу, выбор ограниченного текстового окна и исключение
ошибочных/частичных ответов. Новый контекст полностью заменяет старый, явный
`reset_context` начинает новую тему, не удаляя историю. Миграция `0005` сохраняет
сбросы и снимок эффективного контекста каждого ответа; он доступен в SSE `context`
и истории. Граница темы сохраняется и после выбора нового контекста; предложения
задач предыдущих тем остаются в истории, но исключаются из запроса к модели.
Сценарий со сбросом проверен в тестовом чате с AIAI.BY и после перезапуска сервиса.
Инструмент брака использует контекст для недостающих аргументов, возвращает
недостающие поля для уточнения и не игнорирует неподдержанные product/department.
Расширение правил Context Manager по мере появления новых адаптеров:

- проверить модуль, сущность и фильтры;
- определить эффективный контекст вопроса и его наследование из истории;
- ограничить запрос разрешёнными подразделениями и сущностями;
- собрать подходящие источники и отметить отсутствующие или устаревшие данные;
- ограничить объём информации, передаваемой модели.

До готовности основного backend использовать отдельный синтетический адаптер с
тем же интерфейсом, что и реальный PulseClient. Сценарии: рост брака, норма,
недостаточно данных, запрещённая сущность, недоступный источник. Не разрабатывать
бизнес-монолит платформы внутри AI-сервиса.

**Готово, когда:** инструменты возвращают типизированные результаты; право на
производство не открывает финансы; смена адаптера не требует изменения API чата.

## 5. Этап 2 — настоящий цикл анализа с tool calling

Начат и подключён к чату: потоковый разбор function calls, цикл «модель → инструмент →
результат → модель», до 6 шагов/8 вызовов, таймаут инструмента 10 секунд.
Добавлены `app/agent.py`, `app/agent_provider.py` и миграция `0003` для `tool_calls`
и `messages.sources`. Вызовы и их результаты сохраняются; источники восстанавливаются
из истории. При потере права на ранее использованные данные доступ к диалогу
закрывается консервативно по сохранённым правам/области подразделений вызова.
Внутренние reasoning-фрагменты используются только для продолжения текущего
протокольного обмена с моделью, не выдаются в SSE и не пишутся в журнал инструментов.
Настоящий вызов `get_defect_summary` через AIAI.BY проверен на новом синтетическом диалоге.
Добавлены поиск знаний и синтетический сценарий предложений действий (этапы 4–5).
Вынесен Context Manager для текущих модулей и инструментов. Расширение остальных
адаптеров и учёт стоимости остаются следующими работами; этап целиком ещё не завершён.

**Результат:** модель сама запрашивает необходимые данные и формирует ответ с источниками.

Оркестратор выполняет цикл:

1. Получить историю, контекст, актуальные права и выбранный режим.
2. Передать модели описание доступных инструментов.
3. Проверить имя и аргументы предложенного вызова на сервере.
4. Исполнить разрешённый инструмент и сохранить его результат.
5. Передать результат модели для продолжения или формирования ответа.
6. Передать пользователю итоговый текст, источники и статус завершения.

Начальные защитные пределы: до 6 шагов оркестратора и до 8 вызовов инструментов на
один вопрос. Значения конфигурируются; достижение лимита даёт понятный результат,
а не бесконечный цикл. Независимые запросы данных можно выполнять параллельно.

Числовые вычисления выполнять в коде: доли, процентные пункты, сравнение периодов,
вклад групп и согласованные финансовые формулы. Различать количество дефектов и
количество бракованных заказов. Проверять нулевой знаменатель и сопоставимость периодов.
Модель объясняет результаты, отделяет гипотезы от подтверждённых фактов.

Оба режима используют одинаковые данные, права и инструменты. `deep` меняет
рассуждение и бюджет анализа; он не получает дополнительных полномочий.
Поддержку tool calling выбранной моделью через AIAI.BY проверить отдельным коротким
синтетическим запросом: работоспособность обычного чата сама по себе этого не доказывает.

Источники формирует сервер из результатов инструментов. В них должны быть ID,
тип, период, время обновления, применённые фильтры, признак synthetic и ссылка на
сущность/документ. Отсутствующее значение не подменяется нулём.

Добавлен журнал `analysis_runs` (миграция `0006`): модель/режим, traceId, подготовка,
время до первого текста, общая длительность, попытки/повторы провайдера, число и время
инструментов, безопасный код ошибки и только полученный отчёт токенов. Неизвестный
расход остаётся null; накопительные usage-чанки не суммируются дважды, частичный
расход отмечается отдельно. Replay не создаёт запись, отмена и восстановление после
сбоя процесса сохраняют соответствующий статус. Секреты и тексты в журнал не копируются.
Доступны SSE `diagnostics`, `messages[].diagnostics` и `GET /assistant/conversations/{id}/runs`.
`tool_end` содержит длительность вызова. Тестовый frontend показывает компактные замеры
и раскрываемые подробности. Проверены завершение, retry, обрыв, отмена и восстановление;
также проверен короткий запрос через AIAI.BY и восстановление реальных замеров/usage
после обновления страницы. Стоимость в деньгах не рассчитывается без согласованных
тарифов провайдера.

**Готово, когда:** вопрос о браке запускает подходящие инструменты, ответ содержит
проверяемые расчёты и источники; при отсутствии данных ассистент объясняет пробел.

Это первый самостоятельный результат: **аналитический ассистент с инструментами чтения**.

## 6. Этап 3 — подключение к будущему интерфейсу платформы

Дополнение к продуктовому сценарию: персональная сводка и пакет действий по роли.
Это запланированное расширение; наличие аналогичной функции в ERP компании не
установлено. Финальный дизайн реализует frontend-команда.

Разделять два механизма: серверная ACL определяет разрешённые данные и действия;
предпочтения представления определяют краткость, группировку и раскрытие подробностей.
Кнопка «Подробнее» не расширяет полномочия. Роль директора сама по себе не означает
доступ ко всем кадровым, персональным и финансовым данным: применяется согласованная ACL.

Директор по умолчанию видит сводку существенных отклонений, затронутые заказы,
последствия для сроков/затрат при наличии расчётов, ответственного и требуемое решение.
Карточка заказа раскрывает расчёты, источники и историю действий в пределах прав.
Руководитель производства видит очередь, затронутые заказы и допустимые варианты
восстановления; технолог — дефекты, материалы, инструкции и проверочные гипотезы;
оператор — свои разрешённые задания и следующий шаг; клиентский менеджер — подтверждённый
клиентский эффект и черновик сообщения. Названия ролей и границы согласовать с компанией.

Один кейс имеет общие ID, версию/время среза и проверенные расчёты. Ролевые представления
используют эти факты, не создают независимые противоречащие друг другу версии события.
Подробности загружаются по запросу с новой проверкой ACL. Краткий текст тоже формируется
после фильтрации прав; скрытая деталь не должна утекать через сводку или число событий.
Развёрнутый режим рассуждения LLM и кнопка раскрытия карточки — независимые функции.

Для действий: подготовить связанную задачу специалисту, сводку руководителю и черновик
сообщения клиенту по одному выбранному решению. Уведомлять клиента о подтверждённом
влиянии на его заказ, не о каждом внутреннем дефекте. Внешние отправки и изменения
производственного плана требуют соответствующего подтверждения и прав; автоматическая
рассылка не включается. Сначала показать один синтетический кейс для разных ролей.

Подготовлен независимый `clients/javascript/assistant-client.mjs`: capabilities,
диалоги/история/диагностика, UTF-8/SSE, AbortSignal и подтверждение/отклонение карточек.
Стабильный ключ отправки обязателен, автоматических повторов POST нет. Проверены
разбитые сетевые чанки, CRLF/многострочный JSON, 429, отмена и преждевременный EOF.
Это клиент для нового интерфейса, а не перенос дизайна тестовой страницы.
Дополнительно выполнен живой HTTP-прогон клиента на локальном сервисе: readiness,
demo-вход и capabilities с общими лимитами. Обращений к LLM/«Пульсу» для этого не было.

**Результат:** другой frontend подключается к сервису без переноса его логики.

Передать frontend-разработчику:

- OpenAPI и примеры HTTP/SSE;
- структуру контекста из бизнес-модуля;
- описание capabilities и выбранного режима;
- восстановление истории и состояния незавершённого ответа;
- отображение источников, промежуточных статусов и ошибок;
- правила отправки JWT и отмены через AbortController.

Закрепить разделение: сервер сообщает смысл события, клиент выбирает его визуальное
отображение. В API не должны попадать CSS, готовые HTML-компоненты или привязка к
расположению виджета. Показанные источники и предложения должны восстанавливаться
из истории, а не существовать только в живом SSE-потоке.

Для интеграции можно подключить AI API через общий gateway платформы либо через
отдельный origin с настроенным CORS. Секрет провайдера остаётся только на backend.

**Готово, когда:** вопрос из модуля производства и вопрос с общей страницы ассистента
обрабатываются одинаковым сервисом; после обновления страницы история восстанавливается.

## 7. Этап 4 — знания и RAG

Реализован первый шаг: `app/knowledge.py`, инструменты `search_knowledge` и
`read_knowledge_article`, синтетическая инструкция термопереплёта и закрытый документ
для проверки ACL. Реальный поиск подключён к существующему `/kb/search` с JWT
пользователя, проверяет метаданные и ограничивает объём фрагментов. Название,
ID, версия, дата и признак synthetic сохраняются в источниках SSE/истории.
Текущий доступ к документам повторно проверяется перед чтением истории или
продолжением диалога. Полное чтение статей доступно только синтетическому адаптеру:
схема реального ответа `/kb/articles/{id}` отсутствует и требует согласования.
Сквозной сценарий с моделью-подставкой и отзывом ACL проверен; реальный API базы
знаний ещё не был доступен для проверки. Отдельный новый синтетический диалог
проверен с настоящей моделью AIAI.BY через тестовый чат: поиск → чтение статьи →
ответ с ID/версией → восстановление ответа и источников после обновления страницы.
Собственный индекс не создавался.

**Результат:** ответы опираются на доступные регламенты и инструкции.

Сначала подключить предусмотренные `/kb/search` и `/kb/articles/{id}` как инструменты.
Уточнить, возвращает ли поиск подходящие фрагменты и какой поиск уже реализован
на стороне платформы. Собственный индекс добавлять при подтверждённой необходимости.

Проверять доступ до передачи фрагментов модели. Передавать название, ID, версию,
время обновления и фрагмент, на который можно сослаться. Инструкции из найденных
документов считаются содержимым источника, а не командами для смены поведения сервиса.
При отсутствии подтверждения в документах ассистент сообщает, что ответа не нашёл.

Если понадобится собственный индекс, отдельно реализовать загрузку и разбиение
документов, индексирование, обновление/удаление версий и фильтрацию по ACL.
Не создавать неограниченную копию корпоративных документов без модели доступа.

**Готово, когда:** запрос об обслуживании станка даёт ответ со ссылкой на нужную
инструкцию, а закрытый документ не попадает ни в ответ, ни в контекст LLM.

## 8. Этап 5 — предложения действий, подтверждение и аудит

Реализован первый синтетический сценарий: модель вызывает `propose_task`, предложение
сохраняется и возвращается в SSE/истории; подтверждение создаёт одну локальную
синтетическую задачу, отклонение ничего не создаёт. Внедрены срок подтверждения,
повторная проверка прав/станка и аудит операций. Добавлены миграция `0004` и API
proposals. Тестовый интерфейс показывает карточки, будущий frontend использует тот
же контракт. Реальный POST /tasks, согласование исполнителей и обработка неопределённого
результата внешней записи по ключу идемпотентности остаются следующими работами.

**Результат:** ассистент может создать задачу после подтверждения пользователя.

Первое действие — только создание задачи через `POST /tasks`.
До его внедрения согласовать обязательные поля, идентификаторы исполнителей,
способ получения доступных исполнителей и идемпотентность основного backend.

Реализованы маршруты для синтетического сценария:

- `GET /assistant/proposals`
- `POST /assistant/proposals/{id}/confirm`
- `POST /assistant/proposals/{id}/reject`

Предложение хранит владельца, тип операции, точный payload, предпросмотр, срок
действия и состояние. Состояния согласовать с существующим Proposal:
`pending`, `confirmed`, `rejected`, `executed`, `failed`.

Подтверждение относится к конкретному сохранённому предложению. После изменения
payload требуется новое подтверждение. При подтверждении повторно проверить
права, доступ к сущностям и актуальность предложения.

Защитить операцию от двойного клика и параллельных запросов. Передавать стабильный
ключ идемпотентности в основной backend. При сетевом таймауте после отправки операции
уточнять результат по этому ключу, а не создавать вторую задачу вслепую.

Аудит фиксирует инициатора, инструмент, разрешение/отказ, подтверждение, внешний
результат и traceId. Токены и ключи не сохраняются в журнал. Успех в чате показывается
только после подтверждённого результата основного API, со ссылкой на созданную задачу.

**Готово, когда:** без подтверждения задача не создаётся; повтор подтверждения
не создаёт дубликат; в истории и аудите виден фактический результат.

Это второй результат: **сквозной MVP от вопроса о браке до созданной задачи**.

## 9. Этап 6 — рабочее развёртывание

**Результат:** сервис подключён к настоящей платформе и запускается воспроизводимо.

- PostgreSQL — постоянное хранилище, миграции выполняются отдельным шагом.
- Собственный Docker-образ и конфигурация окружения; секреты передаются при запуске.
- JWT платформы проверяется по согласованным параметрам и реальному `/me`.
- Для рабочего окружения: `AI_AUTH_MODE=jwt`, `AI_DEMO_UI_ENABLED=false`,
  `AI_ALLOW_DEMO_LLM=false`; тестовая выдача токенов отсутствует.
- Передача бизнес-данных внешнему провайдеру соответствует согласованной политике
  компании; в запрос попадают только необходимые пользователю данные.
- Gateway пропускает SSE без буферизации и поддерживает таймаут подробного режима.
- Проверяются readiness, перезапуск, сохранность истории и истечение блокировок.
- Добавляются ограничения запросов и расходов, сроки хранения истории и аудита,
  резервное копирование и порядок восстановления.
- Наблюдаемость различает задержку до первого текста, общее время, этапы инструментов
  и ошибки провайдера. Отдельно учитывать время интерфейсной анимации.

**Готово, когда:** будущий frontend проходит один согласованный сценарий с реальным
профилем, правами и данными; перезапуск сервиса сохраняет историю; ошибки диагностируются
по traceId без раскрытия секретов. Сам Docker-запуск должен быть реально проверен,
наличие Dockerfile не считается завершённым развёртыванием.

## 10. Порядок работ и короткие проверки

| Очередь | Работа | Зависимость | Результат для демонстрации |
| --- | --- | --- | --- |
| 1 | Контракты и недостающие схемы | Договорённость с backend/frontend | Команда подключается к одному API |
| 2 | PulseClient, Context Manager, инструменты чтения | Контракты; сначала синтетический адаптер | Ассистент получает данные через функции |
| 3 | Tool calling, вычисления, источники, журнал запусков | Инструменты чтения | Обоснованный разбор роста брака |
| 4 | Подключение будущего frontend | Контракт чата; можно делать параллельно с 2–3 | Ассистент доступен из модулей платформы |
| 5 | Поиск знаний | Контракт и ACL базы знаний | Ответ со ссылкой на инструкцию |
| 6 | Proposal и создание задачи | Аудит, права, готовый POST /tasks | Подтверждённая задача без дублей |
| 7 | Реальная интеграция и развёртывание | Рабочий backend, JWT, окружение | Воспроизводимый сквозной MVP |

Проверки выполняются по изменённой функции: один успешный сценарий и существенная
ошибка/отказ. Не повторять весь набор тестов после каждой мелкой правки. Полный прогон —
по просьбе пользователя либо при существенных изменениях авторизации, хранения
и других общих механизмов. Для UI достаточно короткой проверки изменённого сценария.

Вопросы для согласования перед реальной интеграцией: где будет основной backend,
кто поддерживает его контракт, как выдаются JWT, какие данные доступны для демонстрации
и какая операция входит в первый подтверждаемый сценарий. Эти вопросы не мешают
начать реализацию адаптеров и инструментов на синтетическом наборе.

## 11. Что оставляем на следующие версии

После сквозного MVP: дополнительные модули, утренние сводки, уведомления, проверка
эффекта решений и более сложные действия. Для каждой функции отдельно согласовать
данные, права и критерий полезности. Мультиагентность и отдельный собственный поисковый
индекс не являются обязательными условиями текущего плана.

Проверка согласованности всего backend выявила и устранила устаревшие предположения
тестов о порядке SSE и неполную тестовую JWT-конфигурацию. Экспорт общего OpenAPI
исправлен для const → enum и канонических шаблонов proposals без дублей. Оба OpenAPI
валидируются, несвязанные маршруты платформы сохраняются. Проверки не включали
реальный «Пульс», Docker или рабочий PostgreSQL.

Реализовано ограничение новых генераций на пользователя через БД (миграция `0007`):
скользящие минутная/суточная квоты и активные lease параллельных ответов. Проверка
и создание сообщения атомарны, повтор завершённого запроса не расходует квоту.
Отказ — 429 с Retry-After до запуска LLM. Настройки публикуются в capabilities;
тестовый frontend сохраняет запрос и показывает ожидание. Проверены гонка двух
экземпляров Repository на SQLite, независимость пользователей, replay и смена окна.
Денежный/токенный бюджет и глобальные ограничения пока не реализованы.

Добавлены общие квоты всех пользователей (миграция `0008`): 60/минуту, 1000/24ч,
8 одновременных генераций, настройки и capabilities. Общая блокировка берётся перед
блокировкой пользователя; replay не расходует квоту. Проверена гонка двух пользователей.

Операционные материалы: `docs/operations.md`, шаблон SSE gateway и отдельный
container job в CI для Compose/PostgreSQL/migrations/HTTP smoke. На текущем компьютере
Docker отсутствует: контейнерный запуск не объявляется проверенным. Автоматическое
удаление истории не включено до согласования retention; текущее хранилище не очищалось.

Оставшиеся зависимости: **готовый backend «Пульса» и согласованные контракты; Docker/
рабочий PostgreSQL для приёмки; сроки хранения истории/аудита; тарифы и полный учёт
usage для денежного бюджета.** Лимиты числа запусков не заменяют точный денежный потолок.
