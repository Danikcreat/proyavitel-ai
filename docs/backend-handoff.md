# Требования к backend «Пульса»

Статус: предложение для согласования. Интеграция отложена по решению владельца проекта
до готовности основного backend. Этот документ не меняет исходный OpenAPI и не
включает реальные записи задач. AI-сервис уже работает отдельно на синтетических данных.

## Уже можно подключать

- JWT RS256: согласовать issuer, audience и публичный ключ либо JWKS URL.
- `/me`: `{id, permissions: string[], departmentScope: string[]}`. id должен совпадать
  с JWT sub. Права перечитываются на каждом запросе AI, claims не заменяют профиль.
- `/equipment/stations`: ACL-фильтрованный массив Station по текущему Bearer JWT.
- `/kb/search?q=...&ai=true`: массив `{document, fragment, score}` из исходной схемы.
  Нужны ID, название, aclLevel, целая версия >=1 и updatedAtUtc с часовым поясом.
  Доступ к `/kb/articles/{id}` должен повторно проверять ACL, включая отзыв доступа.

Согласовать имена прав: assistant:use, production:read, equipment:read, kb:read,
tasks:create и остальные `<module>:read`. Сейчас это соглашение AI-сервиса.
Права на производство должны позволять проверить доступ к выбранному станку:
нельзя требовать несвязанное equipment:read только ради проверки контекста производства.
Нужна связь station → department либо отдельная проверка ACL. До её появления
комбинация «станок + подразделение» в JWT-контексте закрыта.

## Агрегат качества — недостающая схема

Согласовать маршрут и параметры station_id, start, end. Не выводить число
бракованных заказов из количества отдельных дефектов. Предлагаемый DTO уже
соответствует внутреннему QualitySummary:

```json
{
  "station_id": "st-03",
  "current": {"start": "2026-11-01", "end": "2026-11-11", "total_orders": 4000, "defective_orders": 240},
  "previous": {"start": "2026-10-21", "end": "2026-10-31", "total_orders": 4000, "defective_orders": 80}
}
```

Это синтетический пример. Дополнительно согласовать updated_at, часовой пояс,
включение конечной даты, правила прошлого периода, фильтры продукта/подразделения,
свежесть среза и единицу наблюдения. defective_orders <= total_orders, целые числа
неотрицательны; отсутствие наблюдений отличается от нуля брака. Backend проверяет
доступ к станку и ограничивает выборку до формирования агрегата. Нынешний
GET /production/defects не имеет схемы/знаменателя и не подходит для расчёта доли.

## Полная статья

Предлагаемый DTO `GET /kb/articles/{id}`:

```json
{
  "document": {"id": "instruction-1", "title": "Инструкция", "aclLevel": "department", "version": 1, "updatedAtUtc": "2026-11-11T09:00:00Z"},
  "content": "Текст утверждённой инструкции"
}
```

Уточнить формат текста, предел размера, версии и поведение удалённой/закрытой статьи.
Не принимать от AI список якобы разрешённых документов. JWT пользователя — источник
авторизации; поиск и чтение проверяют её независимо. Вложения и собственный
векторный индекс в первый контракт не включены.

## Задачи и исполнители

В исходном Task нет описания, станка, обязательных полей и схемы успешного ответа
POST /tasks. Значение ownerId и его связь с assigneeId фильтра тоже нужно уточнить.
Нужен серверный список доступных исполнителей; AI не будет придумывать их ID.

Предлагаем согласовать вход: title, description, stationId, assigneeId, nullable
deadline, source=assistant, sourceRef=<proposal UUID>. Возврат: ID, точные сохранённые
поля, статус и стабильная ссылка для frontend. Названия полей пока не считаются
утверждёнными и не отправляются существующему POST /tasks.

Обязательно согласовать идемпотентность:

1. Стабильный Idempotency-Key одной подтверждённой карточки, область пользователя/tenant.
2. Одинаковые payload/key возвращают тот же ID, изменённое тело даёт 409.
3. Параллельные запросы не создают две задачи.
4. После таймаута AI может проверить результат по ключу. Маршрут и ответ такой
   проверки согласовать отдельно; неопределённый результат нельзя трактовать как отказ.
5. Срок хранения ключа покрывает весь период восстановления AI-запуска.
6. Права, доступ к станку и исполнителю перепроверяются в backend в момент записи.

AI хранит неизменяемую карточку и подтверждение пользователя. До подтверждения
POST /tasks не вызывается. При неопределённом результате интерфейс не сообщает об
успешном создании и не повторяет запись вслепую.

## Критерий совместной приёмки

На отдельном тестовом окружении: JWT с ограниченными правами → вопрос о браке →
правильные доли/п.п. → источник → инструкция → предложение задачи → подтверждение →
одна настоящая задача. Отдельно проверить запрещённый станок/документ, пустые данные,
отзыв прав, двойной клик, обрыв после записи, повтор с тем же ключом и перезапуск AI.
Для этого нужны base URL, параметры JWT и тестовые аккаунты с заранее известной ACL.
JWT и ключи не передавать в документах/чатах: использовать настройки окружения.
