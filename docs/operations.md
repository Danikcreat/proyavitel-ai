# Запуск и восстановление автономного AI-сервиса

Интеграция с «Пульсом» отложена. Локальный стенд — demo auth + синтетические данные;
при AI_MODE=llm тестовые сообщения отправляются настроенному провайдеру. Код рабочего
развёртывания подготовлен, но Docker отсутствует на текущем компьютере, поэтому
запуск образа и PostgreSQL здесь не считаются проверенными.

## Локальный запуск

Из корня проекта, не выводя содержимое .env:

```sh
ai-service/.venv/bin/alembic -c ai-service/alembic.ini upgrade head
ai-service/.venv/bin/uvicorn app.main:create_app --factory --app-dir ai-service --host 127.0.0.1 --port 8081 --no-access-log
```

Readiness проверяет наличие основных таблиц; миграции выполняются до старта. Python
стенда находится в .runtime/python, не во временной папке ОС. Не удаляйте локальную
БД при перезапуске. Проверьте `/health/ready` и историю существующего диалога.
Новые замеры — в `/assistant/conversations/{id}/runs`; причина ошибки связана с traceId.

## Контейнеры

На машине с Docker Compose: `python3 scripts/init_demo.py`, затем
`docker compose up --build -d --wait`. Секреты создаются только если .env ещё нет;
существующий .env не перезаписывается. Compose запускает PostgreSQL, миграцию и API
с постоянным volume. Не используйте `down --volumes` для рабочего хранилища.
В CI добавлен отдельный контейнерный прогон; его успешный результат нужно проверить
перед объявлением развёртывания готовым.

До интеграции не переводите стенд на JWT платформы без готовых /me и параметров JWT.
В будущем рабочем окружении: auth_mode=jwt, demo UI выключен, allow_demo_llm=false,
PostgreSQL, секреты в окружении, согласованные CORS origins. Шаблон gateway рядом:
`deploy/nginx-assistant.conf`. Он не публикуется и не меняет настройки компьютера.

## Ограничения расходов

Квоты пользователя: 20 новых ответов/минуту, 200/24ч, 2 параллельно.
Общие квоты: 60/минуту, 1000/24ч, 8 параллельно. Все значения настраиваются и
возвращаются в capabilities.limits. Они применяются ко всем режимам стенда, включая
симулятор; считаются принятые ответы, включая отменённые/неудачные.

Блокировки БД берутся в одном порядке: общая → пользователь → диалог. Они удерживаются
только на время admission, не во время ответа модели. Replay не расходует квоту.
При 429 используйте Retry-After, не повторяйте POST автоматически с новым ключом.
Квоты ограничивают число запусков, но не гарантируют денежный потолок: deep, инструменты
и retry имеют разную стоимость, usage может быть неизвестен. Точный денежный бюджет
остаётся зависимостью от согласованных тарифов и учёта провайдера. До этого задайте
лимит расходов в кабинете провайдера, если он поддерживает такую настройку.

## Сбой и резервные копии

Нормальное завершение/отмена снимают lease. После потери процесса истёкший lease
освобождается при следующем чтении/запросе; запуск помечается interrupted. Неизвестные
метрики не восстанавливаются выдуманными значениями. При обрыве клиент читает историю
или повторяет тот же payload с прежним Idempotency-Key.

Перед миграциями делайте резервную копию. Для SQLite остановите API и копируйте
файл через SQLite backup API; не копируйте работающий файл как обычный документ.
Для PostgreSQL используйте pg_dump с теми же учётными данными окружения, без пароля
в командной строке. Проверяйте восстановление в отдельной БД с отдельным именем,
а не поверх рабочего хранилища. Бэкапы содержат историю: храните их вне Git, с
ограниченным доступом и согласованным сроком хранения.

Retention истории/аудита и удаление резервных копий требуют согласованных сроков.
Автоматическое удаление не включено; существующие диалоги не очищались. До рабочего
развёртывания владелец системы определяет сроки, исключения и порядок восстановления.
