# Подключение frontend

Базовый URL сервиса: `http://localhost:8081`. JWT передаётся в `Authorization: Bearer <token>`.
При общем gateway маршрутизируйте `/assistant/conversations` и вложенные маршруты на AI-сервис;
остальные маршруты — на основной backend.

## Запросы

Создать: `POST /assistant/conversations`, тело `{"title":"Разбор брака"}`.
Ответ `201`: `{id,title,created_at,updated_at}`.
Список: `GET /assistant/conversations?limit=20&offset=0` → `{items,limit,offset}`.
История: `GET /assistant/conversations/{id}` → поля диалога и `messages`.

Сообщение:

```http
POST /assistant/conversations/{id}/messages
Authorization: Bearer <JWT>
Content-Type: application/json
Idempotency-Key: <stable UUID for this send>
```

```json
{
  "text": "Почему вырос процент брака?",
  "context": {
    "module": "production",
    "screen": "station_details",
    "entity": {"type": "station", "id": "st-03"},
    "filters": {"from": "2026-11-01", "to": "2026-11-11"}
  }
}
```

`context` необязателен. Если он отсутствует, используется последний сохранённый контекст
всего диалога, независимо от размера текстового окна LLM. Новый контекст заменяет
предыдущий целиком: старые даты, станок и фильтры не подмешиваются.
`reset_context: true` начинает новую тему без прежнего контекста и без передачи
предшествующих сообщений модели. История в БД не удаляется; проверки доступа к ней
сохраняются. Одновременные `context` и `reset_context: true` дают HTTP 422.
После сброса контекст остаётся пустым до явной передачи нового `context`.

`GET /assistant/conversations/{id}` возвращает `effective_context` для текущей темы.
Каждый ответ имеет сохранённый снимок `messages[].effective_context`. Поля снимка:
`context`, `origin` (`none`, `current`, `inherited`, `cleared`), `source_message_id`,
`topic_start_message_id` (граница последнего сброса), `missing_fields`.
`messages[].reset_context` отмечает начало новой темы. Старые предложения задач
остаются в истории, но не передаются модели в новой теме, даже после выбора нового контекста.
`module` принимает модули исходного OpenAPI (полный enum — в Swagger).
Поддержанные фильтры: `from`, `to`, `department`, `product`. Дополнительные поля отклоняются.
Права из браузера, имена владельцев и claims в теле не принимаются.

## Возможности текущего пользователя

После входа запросите `GET /assistant/capabilities` с тем же Bearer JWT.
Версия формата — `schema_version: "1"`. Ответ персонализирован, имеет
`Cache-Control: private, no-store` и `Vary: Authorization`; не кэшируйте его между
пользователями. Повторяйте запрос при смене профиля/прав или конфигурации модели.
JWT-режим читает актуальный профиль `/me`; сам endpoint не обращается к LLM или
каталогу моделей, не запускает инструменты и не создаёт диалогов.

- `reasoning_modes`: допустимые `standard`/`deep`, таймаут и настроенный лимит токенов
  каждого режима; `null` означает, что лимит провайдера не определён сервисом.
  `simulated=true` отмечает режим без настоящей модели. Список совпадает с проверкой
  `POST .../messages`; для LLM подробный режим пока реализован только для DeepSeek.
- `modules`: модули, разрешённые как UI-контекст по текущим `<module>:read`;
  `entity_types` содержит только типы с реализованной проверкой ACL. Сейчас это
  `station` для production/equipment. `unsupported_filters_with_entity` отмечает
  неподдержанные сочетания; в JWT-режиме подразделение станка пока нельзя проверить.
  `data_tools` связывает модуль с инструментами, но не обещает готовых данных.
- `tools`: функции, объявляемые агенту для этого пользователя. `data_source`
  различает `synthetic` и `platform_api`; при `contract_status=pending` источник
  отсутствует, а `unavailable_reason` объясняет пробел. В частности, реальная
  агрегированная сводка брака пока возвращает unavailable. Полное чтение реальных
  статей не объявляется, так как нет схемы ответа платформы.
- `tool_calling`: включён ли цикл инструментов с текущим LLM-провайдером. В режиме
  симулятора — false, список `tools` пуст. `actions` при этом отдельно описывает право
  подтвердить уже сохранённое предложение, в том числе из прежнего LLM-диалога.
- `actions`: сейчас только `create_task` с `requires_confirmation=true` и
  `execution=synthetic`, если права позволяют. Реальные записи задач не включены
  даже при наличии `tasks:create` в JWT платформы.
- `context_filters`, `features` и `limits`: поддержанные поля контекста, история,
  сброс, источники, диагностика, ограничения текста/истории и агентного цикла.
  `max_quality_period_days` ограничивает разницу `end-start`, а не число дат включительно.

Возможность передать контекст finance/hr не означает наличие инструмента финансов
или кадров. `platform_api` описывает адаптер по контракту, а не результат health check.
Backend заново проверяет права на каждом запросе и вызове инструмента: видимость
кнопок в frontend не является авторизацией. При 403 обновите capabilities, не
повторяйте операции записи автоматически. Неподдержанную версию формата обработайте
явной ошибкой; не подставляйте набор возможностей более привилегированного профиля.

Тестовый чат использует этот endpoint для режимов, своих четырёх пунктов модулей,
лимита ввода и подтверждений; новый frontend может использовать все возвращённые
модули и выбирать собственное отображение. Дизайн интерфейса в контракт не входит.

## События SSE

Дополнительно действуют общие для всех пользователей и режимов квоты:
`AI_GLOBAL_GENERATION_REQUESTS_PER_MINUTE=60`, `AI_GLOBAL_GENERATION_REQUESTS_PER_DAY=1000`,
`AI_GLOBAL_MAX_CONCURRENT_GENERATIONS=8`. Они публикуются в capabilities.limits,
используют общую блокировку БД и возвращают тот же 429/Retry-After до запуска LLM.
Replay проверяется до расходования обеих квот. Счётчики других пользователей наружу
не передаются. Это общий потолок числа запусков, а не стоимости в деньгах.

Готовый fetch/SSE-клиент будущего интерфейса — `clients/javascript/assistant-client.mjs`.
Он не хранит JWT, не повторяет POST автоматически и требует стабильный ключ отправки.
Пример использования и правила обработки ошибок — в README рядом с клиентом.

Новые генерации ограничены на пользователя: по умолчанию 20 за скользящую минуту,
200 за последние 24 часа, до двух одновременно во всех его диалогах. Настройки:
`AI_GENERATION_REQUESTS_PER_MINUTE`, `AI_GENERATION_REQUESTS_PER_DAY`,
`AI_MAX_CONCURRENT_GENERATIONS_PER_USER`; значения также доступны в `capabilities.limits`.
Admission выполняется в общей БД в транзакции создания пары сообщений; блокировка
по пользователю синхронизирует процессы. Отказ возвращает HTTP 429 RFC 7807 с
`Retry-After` в секундах до SSE, не создаёт сообщения и не вызывает LLM. Активный
ответ в том же диалоге по-прежнему даёт 409. Replay завершённого ответа проходит
без расходования квоты; ключ с изменённым телом даёт 409.

Завершение и отмена освобождают параллельный слот; после сбоя процесса слот
освобождается по сроку lease. Минутная/суточная квоты считают принятые новые ответы,
включая отменённые и неудачные: провайдер мог уже обработать запрос. Эти ограничения
не являются точным бюджетом токенов или денег; глобальный бюджет провайдера и
ограничение всех HTTP-запросов на gateway остаются отдельными задачами. Проверки
конкуренции выполнены на SQLite; рабочий PostgreSQL требует интеграционного прогона.
Frontend показывает ожидание и сохраняет текст запроса; автоматически новый POST
не повторяет. `Retry-After` доступен через CORS.

Перед `done` для новых ответов приходит `diagnostics` — сохранённая запись запуска.
Та же запись находится в `messages[].diagnostics` и отдельном постраничном
`GET /assistant/conversations/{id}/runs?limit=20&offset=0`. Доступ проверяется по
владельцу диалога и текущим правам на его источники/контексты. Старые ответы могут
не иметь диагностики. Replay возвращает исходную запись и traceId, не новый запуск.

Времена измеряются на backend в миллисекундах: `preparation_ms` — от приёма HTTP
до начала генерации (включая авторизацию, историю и проверки контекста),
`first_text_ms` — до первого непустого фрагмента текста, `total_ms` — до завершения
генерации/закрытия провайдера. Финальная запись в БД, доставка сети и анимация frontend
в `total_ms` не входят. `first_text_ms=null` означает, что текст не получен или замер
не сохранился. Время модели и инструментов — отдельные измерения, а не слагаемые,
из которых нужно восстанавливать `total_ms`.

`provider_calls` считает попытки совместимого LLM-провайдера, включая неудачные;
`provider_retries` — повторные попытки, которые действительно начались.
`provider_time_ms` суммирует время попыток (включая проверку каталога, если она нужна),
но не задержку backoff между ними. `tool_calls` учитывает и запрещённые вызовы,
`tool_time_ms` — их обработку/исполнение; `tool_end.duration_ms` — отдельный вызов.
Внутренние рассуждения не считаются первым видимым текстом и не сохраняются в журнал.

`reported_prompt_tokens`, `reported_completion_tokens`, `reported_total_tokens`
содержат сумму последнего корректного `usage` каждой попытки; накопительные чанки
одной попытки не складываются между собой. `usage_status`: `unknown` — ни одного
корректного отчёта, значения `null`; `partial` — известен лишь расход части попыток
или поток оборвался; `complete` — отчёты получены для всех завершённых попыток.
Это отчёт провайдера, не расчёт стоимости или баланса. Запросы к провайдеру не
получают новых обязательных параметров ради статистики.

Записи создаются для принятых сообщений, статусы `preparing`/`running` меняются на
`completed`, `failed`, `cancelled` или `interrupted`. Пока запуск идёт, счётчики могут
быть `null`; финальные замеры пишутся вместе с итоговым статусом сообщения. При
восстановлении после потери процесса точная длительность и незаписанные счётчики
остаются неизвестными. `error_code` содержит безопасный код, без тела исключения.

Событие `context` содержит тот же снимок эффективного контекста. При replay возвращается
снимок исходного ответа; он не пересчитывается по более поздним сообщениям.
Событие добавляется после начального `sources`; старые клиенты могут его игнорировать.

`get_defect_summary` может принимать неполные аргументы: недостающие `station_id`,
`start`, `end` сервер подставляет из эффективного контекста производства/оборудования.
Явные аргументы имеют приоритет и проходят проверку прав и совместного периода.
Если полей не хватает, инструмент возвращает `insufficient_data` / `missing_context_fields`
со списком `missing_fields`; модель должна запросить уточнение. Фильтры `product` и
`department` пока не поддерживаются этим агрегатом: вместо игнорирования возвращается
`unsupported_context_filters`. Фактически применённые значения сохраняются в
`sources[].filters` и результате инструмента `applied_filters`.

Предложения задач: SSE `proposal` содержит `{proposal: TaskProposalOut}`; тот же объект
восстанавливается из `GET /assistant/conversations/{id}` в поле `proposals`.
`GET /assistant/proposals?conversation_id=<UUID>` возвращает доступные собственные предложения.
Подтверждение: `POST /assistant/proposals/{id}/confirm`; отклонение:
`POST /assistant/proposals/{id}/reject`. Подтверждается только сохранённый payload,
передача нового содержимого в confirm не изменяет задачу. Повтор confirm возвращает
исходный результат без новой задачи. `409` — уже отклонено или истёк срок подтверждения.
В текущем demo результат всегда `synthetic=true`: это локальная тестовая задача,
а не операция основного backend. В режиме JWT инструмент создания предложений пока
не объявляется, и выполнение реальных задач не подключено.
В одном ответе создаётся не больше одного предложения. Срок подтверждения — один час.
Права проверяются повторно при подтверждении и отклонении; фактические состояния
предложений передаются модели в следующем сообщении диалога.

Агентный цикл добавляет `tool_start` (`tool`, `call_id`) и `tool_end`
(`tool`, `call_id`, `status`, `code`). Статус инструмента может быть `ok`, `denied`,
`insufficient_data`, `unavailable`. Событие `sources` может повторяться и содержит
весь накопленный список источников текущего ответа. Источники также сохраняются
в `messages[].sources`. Поле `synthetic` определяет метку тестовых данных;
`updated_at=null` означает, что свежесть источника неизвестна.

Инструменты знаний требуют `kb:read`. `search_knowledge` принимает `{query}`,
возвращает до пяти фрагментов по 4000 символов. `read_knowledge_article` принимает
`{document_id}` и сейчас объявляется только для синтетического адаптера: тело
реального `/kb/articles/{id}` ещё не описано контрактом. Источники документов имеют
`type: "knowledge"`, `id`, `title`, `version`, `updated_at`, `endpoint`, `synthetic`.
`endpoint` — относительный путь API документа, а не URL страницы frontend.
Пустой поиск даёт `insufficient_data` / `knowledge_not_found`, недоступный или
некорректный источник — `unavailable`, без выдуманных инструкций.
При чтении истории и перед продолжением диалога сервер повторно проверяет ACL
каждого использованного документа; отказ даёт HTTP 403, недоступность проверки — 503.
Это консервативно закрывает весь затронутый диалог, включая идемпотентный replay.

В теле сообщения поддерживается `reasoning_mode`: `standard` (по умолчанию) или
`deep`. Режим сохраняется в истории и возвращается в `meta.reasoning_mode`.
`deep` включает рассуждения DeepSeek; внутренний текст рассуждений не передаётся
клиенту. Дополнительные SSE-события `status` содержат `phase`: `waiting`, `thinking`,
`answering`. После начала текста приходят обычные `delta` без буферизации на сервере.

Каждое событие состоит из `event: ...`, строки `data: <JSON>` и пустой строки.
Поток передаётся в UTF-8; границы сетевых чанков не совпадают с границами событий.

| Событие | Данные |
| --- | --- |
| `meta` | `conversation_id`, `user_message_id`, `assistant_message_id`, `mode`, `replay` |
| `sources` | `{items:[{id,synthetic,updated_at,period}]}`; пустой список, если источников нет |
| `context` | `{context,origin,source_message_id,missing_fields}`; снимок выбранного контекста |
| `delta` | `{delta:"следующая часть ответа"}` |
| `error` | `{code:"generation_failed" или "generation_timeout",traceId}` |
| `diagnostics` | Запись запуска: trace_id, статусы, времена, счётчики и доступный отчёт токенов |
| `done` | `{message_id,status}` |

Нормальный порядок: `meta`, `sources`, `context`, `status`, события инструментов/источников, `delta` несколько раз, `diagnostics`, `done(completed)`.
При ошибке: частичный ответ, `error`, `done(failed)`.
Heartbeat — комментарий `: heartbeat`, его нужно игнорировать.
При идемпотентном повторе: `meta(replay=true)`, сохранённый текст в `delta`, при необходимости `error`, `done`.
При replay сохранённые `sources` и `context` повторяются, если присутствуют у исходного ответа.
В replay ошибки `code` могут быть `failed`, `cancelled`, `interrupted`.
HTTP 200 сам по себе не означает успешное завершение — проверяйте `done.status`.

## Пример чтения в браузере

Используйте `fetch`: нативный `EventSource` не отправляет POST-тело и Bearer-заголовок.

```javascript
async function sendMessage({ baseUrl, token, conversationId, body, requestKey, onEvent, signal }) {
  const response = await fetch(`${baseUrl}/assistant/conversations/${conversationId}/messages`, {
    method: "POST",
    signal,
    headers: {
      Authorization: `Bearer ${token}`,
      "Content-Type": "application/json",
      "Idempotency-Key": requestKey,
    },
    body: JSON.stringify(body),
  });
  if (!response.ok) throw await response.json();
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  let completed = false;
  try {
    while (true) {
      const { value, done } = await reader.read();
      buffer += decoder.decode(value, { stream: !done });
      let boundary;
      while ((boundary = buffer.indexOf("\n\n")) !== -1) {
        const frame = buffer.slice(0, boundary);
        buffer = buffer.slice(boundary + 2);
        const lines = frame.split("\n");
        const event = lines.find(line => line.startsWith("event: "))?.slice(7);
        const data = lines.filter(line => line.startsWith("data: ")).map(line => line.slice(6)).join("\n");
        if (event && data) {
          const payload = JSON.parse(data);
          if (event === "done") completed = true;
          onEvent(event, payload);
        }
      }
      if (done) break;
    }
    if (!completed) throw new Error("Поток оборван. Обновите историю диалога.");
  } finally {
    await reader.cancel();
    reader.releaseLock();
  }
}
```

Отмена — через `AbortController.abort()`. После отмены обновите историю:
она содержит частичный ответ со статусом `cancelled`. При потере соединения
используйте тот же `requestKey`, чтобы избежать повторной генерации.

JWT выдаёт основной backend. Demo-токены генерируются локальным CLI из README;
demo-секрет и ключ LLM никогда не передаются frontend.
